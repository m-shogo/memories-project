## Material failure — prospective canonical learning authority alias

- **Symptom:** The canonical learning validator rejected symlinked leaves and parent-directory aliases but accepted a regular learning/CI authority with multiple hardlink directory entries. A second path could mutate the same inode without changing the canonical path's `is_symlink()` or `resolve()` result. This was a prospective local source-identity gap, **not** an observed production incident.
- **Observed evidence:** An isolated same-filesystem Python fixture created `os.link(authority, alias)`; the canonical leaf remained `is_symlink() == False`, its resolved path was unchanged, and `st_nlink == 2`. The prior five-authority validation loop did not check `st_nlink`. Prior prewrite target/workflow hardlink lessons already established the same inode-alias failure mode for different authority surfaces.
- **Verified root cause:** Symlink and resolved-path checks do not establish uniqueness of a regular-file inode's directory entries.
- **Failed approach:** Treating absence of symlinks and an in-root resolved path as sufficient source-identity proof.
- **Correction:** [`e6c9ef9b`](https://github.com/m-shogo/memories-project/commit/e6c9ef9b4dd14eb5a7d7ea7755a53da1d70a0d89) rejects `st_nlink != 1` for each of the five bound learning/CI authority files. Missing and symlinked-authority checks remain independent.

A hardlink fixture must be observable as a mutation even when the file bytes are unchanged.

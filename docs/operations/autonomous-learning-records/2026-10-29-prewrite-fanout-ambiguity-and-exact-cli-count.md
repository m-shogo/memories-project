## Material failure / coverage undercount and classifier weakness

- **Symptom:** The prewrite fanout parser could silently undercount workflow reachability when YAML used duplicate root/event/path mappings, an unresolved event alias, an inline comment after a path pattern, or a GitHub minimatch construct unsupported by Python `fnmatch`. A new CLI fixture initially accepted a substring count and therefore could accept `10` as proof of `1`.
- **Observed evidence:** The original parser used the first event/path mapping and raw quoted path stripping. The initial CLI check used `"matched workflow count: " + str(count) in result.stdout`; that expression accepts a prefix collision. [`01d43070`](https://github.com/m-shogo/memories-project/commit/01d43070e2bae8ee1313646479a20ea4a6be8d07) added 8 parser self-test cases and 8 actual CLI fixture cases; [`f3a80b58`](https://github.com/m-shogo/memories-project/commit/f3a80b581ea9b5e3cdca8da19210521b6fbca010) corrected the count classifier and added a synthetic `10`-versus-`1` rejection.
- **Verified root cause:** First-match regex parsing and plain `fnmatch` do not establish GitHub Actions YAML/minimatch equivalence. The count prefix weakness was an exact-versus-substring assertion error. The precise source of the large conservative fanout increase below remains **unknown**; do not assert those additional workflows are actual GitHub-triggered executions.
- **Failed approach:** Treating unparsed YAML features as a proven non-match; using a substring match to prove a numeric CLI result.
- **Correction / executable recurrence guard:** The read-only parser now treats duplicate event/path authority, YAML event aliases, quoted/inline comments and unsupported brace/extglob patterns as potentially matching. The CI-bound negative validator executes the real CLI on eight isolated workflows and requires an exact risk/count line and matched workflow identity, with an explicit prefix-collision negative.
- **Observed conservative-scope change:** The same self-test reports possible direct matches increasing from 88 to 151 for the operability validator and from 3 to 68 for the rate-limit validator. This is a **conservative possible-match upper bound**, not a measured increase in CI runs. No production workflow trigger was changed. Root cause of the 65 additional rate-limit classifications has not been independently isolated.
- **Retry condition:** Diagnose the increased conservative match set with read-only per-workflow reason attribution before refining grammar; require a real GitHub Actions YAML/minimatch semantic proof and negative fixtures before reducing any risk count. Do not retry unchanged Quay MinIO HTTP 401, workflow-write permission, large canonical-learning append transport or human-promotion blockers.

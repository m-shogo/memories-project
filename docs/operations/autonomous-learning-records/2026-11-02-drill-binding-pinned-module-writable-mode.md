- **symptom:** The two pinned Python module readers accepted a group/world-writable regular module file and did not explicitly bind permission mode into their pre/post descriptor and pathname identity tuples. No malicious code execution or production incident was observed.
- **evidence:** At `so` HEAD `3dac408f`, both `load_module` helpers required a regular single-link file, a bounded size and stable inode/size/timestamps, but their `before.st_mode` was checked only for regular-file type. The module-source negative suite had hardlink, size, mutation, symlink and FD guards, but no writable-file or permission-race case. Canonical learning guards elsewhere already reject group/world-writable executable authorities.
- **rootCauseOrUnknown:** Verified omission of a writable-mode rejection and explicit permission-mode identity in two executable source readers. Actual exposure to a shared writable checkout is unknown.
- **failedApproach:** Treating a pinned, unchanged regular inode as sufficient executable authority without rejecting an already group/world-writable module source. Relying only on size/timestamps rather than including `st_mode` in source identity.
- **correction:** [3bb9fbf6](https://github.com/m-shogo/memories-project/commit/3bb9fbf6a9a5a4f7e34eea8e538dd1fc5b429efa) rejects `before.st_mode & 0o022` before reading/executing source and includes `st_mode` in the pinned module's pre/post FD, leaf and final pathname identity comparisons, independently in both importers.
- **recurrenceGuard:** The existing CI-reached binding reconcile negative suite now sets a disposable malicious-marker module to mode `0666` and requires rejection before execution; it separately chmods the source during the pinned `os.read` boundary and requires a changed-source rejection. Both cases assert no marker execution, restore `0644` and run for both validator and reconciler; earlier benign positive and all prior negative controls remain.

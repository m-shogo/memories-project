## Material failure — prospective Gitlink/submodule identity ambiguity

- **Symptom:** A prewrite target can live in a nested Git checkout or a repository can contain submodule configuration, yet a direct workflow-path match alone does not prove the audited source belongs to the reviewed parent checkout. This is a prospective static-audit limitation, not a production incident.
- **Observed evidence:** Before `fa0fbe3a`, the prewrite matcher rejected symlinks and hardlinks but never inspected `.gitmodules` or nested `.git` metadata. The reviewed `so` tree currently has no `.gitmodules` or mode-160000 Gitlinks; disposable fixtures create a root `.git` positive, a `.gitmodules` negative and a nested gitdir-file negative.
- **Verified root cause:** Path identity checks alone do not establish Git checkout ownership or Gitlink/submodule closure.
- **Failed approach:** Treating an ordinary repository-relative path and a non-aliased file as sufficient evidence of a single reviewed Git checkout.
- **Correction:** [`fa0fbe3a`](https://github.com/m-shogo/memories-project/commit/fa0fbe3aa3e9cdf187f5d42fced01d761b94b3c7) rejects any root `.gitmodules` metadata (including a symlink) and nested `.git` metadata under the target path; it intentionally allows the repository root's own `.git` marker.
- **Executable recurrence guard:** The fanout self-test and CI-reachable negative validator now require a normal root `.git` positive plus exact-diagnostic `.gitmodules` and nested-checkout CLI negatives. The existing symlink, target-hardlink and workflow-hardlink controls remain.
- **Retry condition:** A more selective submodule exception requires complete Git index mode-160000 and `.gitmodules` parsing, explicit target ownership and checkout-root verification, disposable positive/negative CLI controls, exact-source CI and protected-authority review.

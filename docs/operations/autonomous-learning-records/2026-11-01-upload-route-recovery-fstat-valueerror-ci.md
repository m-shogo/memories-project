## Material failure — secondary recovery probe could mask original stage failure

- **symptom:** If the initial staged `os.fstat(descriptor)` raised `OSError` before stage identity was captured, and the still-owned descriptor's cleanup recovery `os.fstat(untransferred_stage_fd)` then raised an ordinary non-`OSError` (for example `ValueError`), the original exception could be masked. This was a verified source-level exceptional-path gap, **not** an observed production incident.
- **evidence:** Starting code HEAD `11445f11` used `except OSError` for the finalizer's recovery probe, while the existing `unverified-owned` and `unverified-reused` negative cases injected OSError-only permanent failures. The prior append-only lesson `2026-11-01-upload-route-initial-fstat-recovery-and-reused-stage-identity.md` already established the correct fail-closed response to unverified ownership: retain the private name rather than unlink it.
- **rootCauseOrUnknown:** Verified ordinary-exception coverage gap in the second `fstat` handler. Real-world incidence and the descriptor state after an arbitrary injected failure are unknown; neither a pathname match nor a numeric FD match proves an atomic ownership CAS.
- **failedApproach:** Treating OSError-only permanent-fstat negatives as proof that any ordinary recovery-probe failure retains the original publication exception; inferring cleanup ownership from the temporary filename after the probe fails.
- **correction:** [`93aa6c5c`](https://github.com/m-shogo/memories-project/commit/93aa6c5cfac005d2d90154f5147d895f00e51d78) catches ordinary `Exception` from the still-owned recovery `fstat` and adds a bounded exception-type note to the primary failure. An unverified stage name remains untouched.
